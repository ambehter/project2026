# Техническое задание (черновик)

## 1. Общие положения

1.1. Настоящее техническое задание описывает требования к веб-приложению
для поиска ресторанов, просмотра свободных столиков и бронирования столиков,
а также к панели менеджера ресторана.

1.2. Система реализуется как клиент-серверное веб-приложение. Серверная
часть — REST API на PHP 8+ с PDO. Клиентская часть — HTML, CSS,
Vanilla JavaScript. База данных — MySQL. Аутентификация — PHP-сессии.

1.3. Принятые отклонения от первоначального ТЗ: вместо Node.js + Express
используется PHP 8 + PDO; вместо React + TypeScript — Vanilla JS;
вместо PostgreSQL — MySQL; вместо JWT — PHP-сессии. Функциональные
требования при этом сохраняются.

1.4. Основные термины: **гость** — неавторизованный пользователь;
**пользователь** — авторизованный клиент с ролью `user`; **менеджер** —
пользователь с ролью `manager`; **администратор** — пользователь с ролью
`admin`; **бронь** — запись в таблице `bookings`.

---

## 2. Архитектура и стек

2.1. Серверная часть должна быть реализована на PHP 8+ с использованием
PDO для доступа к MySQL.

2.2. Точка входа API — `backend/index.php`. Все запросы к API должны
проходить через единый роутер.

2.3. Базовый путь API: `/restaurant-booking-php/backend/api`.
Клиентский модуль `api.js` использует `API_BASE = '/restaurant-booking-php/backend/api'`.

2.4. Формат обмена — JSON. Успешный ответ оборачивается в объект
`{ "data": ... }`. Ошибка возвращается как `{ "error": "текст ошибки" }`.

2.5. Конфигурация БД задаётся переменными окружения: `DB_HOST`, `DB_NAME`,
`DB_USER`, `DB_PASS`. Значения по умолчанию: `localhost`, `restaurant_booking`,
`root`, пустой пароль.

2.6. PDO должен быть настроен на `ERRMODE_EXCEPTION`, `FETCH_ASSOC`,
`EMULATE_PREPARES = false`.

2.7. Архитектурная схема.

Приложение построено по клиент-серверной схеме. Серверная часть — REST API
на PHP 8+ с доступом к MySQL через PDO. Клиентская часть — статические
HTML-страницы, стили CSS и Vanilla JavaScript, которые обращаются к API
через `fetch` с `credentials: 'include'`. Аутентификация основана
на PHP-сессиях. Никаких сторонних фреймворков, сборщиков и транспайлеров
не используется — это осознанное отклонение от первоначального ТЗ
(Node.js + Express, React + TypeScript, PostgreSQL, JWT), функциональные
требования при этом сохранены.

2.8. Дополнительные фронтенд-технологии (демонстрация).

В рамках демонстрации современных фронтенд-технологий в проект дополнительно
интегрированы **Bootstrap 5** и **React 18** — без отказа от базового стека
(PHP 8+ + Vanilla JS + MySQL). **Bootstrap 5** подключается через CDN jsdelivr
(`https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css`)
и используется для адаптивной сетки, компонентов навигации, кнопок, карточек,
форм и alert-сообщений. **React 18** подключается через CDN unpkg
(`react`, `react-dom`, `@babel/standalone`) и демонстрируется на отдельной
странице `restaurants-react.html`, где каталог ресторанов реализован
как React-приложение с компонентами (`App`, `RestaurantCard`) и хуками
(`useState`, `useEffect`).

Сборщики (Webpack, Vite), npm и Composer **не используются** — это осознанное
решение, сохраняющее простоту развёртывания на типовом хостинге. Основной
backend остаётся на **PHP 8+**, основной frontend — на **Vanilla JS**,
что соответствует пунктам 1.2 и 1.3 исходного ТЗ. Новые технологии добавлены
как демонстрация и не заменяют базовый стек.

Пункт 9.1 ТЗ дополняется страницей `restaurants-react.html` (React-версия
каталога). Пункт 9.6 — CSS-переменными `--rb-primary`, `--rb-bg`, `--rb-text`
и адаптацией под Bootstrap. Все функциональные требования (разделы 4.1–4.6),
требования к БД (раздел 5), REST API (раздел 6), безопасности (раздел 8)
и нефункциональные требования (раздел 10) сохраняются в полном объёме.

## 3. Роли и права доступа

3.1. **Гость** может: просматривать список ресторанов, искать рестораны,
открывать карточку ресторана, проверять доступность столиков,
регистрироваться, входить.

3.2. **Пользователь с ролью `user`** может: создавать бронь, просматривать
свои брони, отменять свои брони, обновлять профиль, менять пароль.

3.3. **Менеджер с ролью `manager`** может: просматривать брони только своих
ресторанов, менять статус брони на `confirmed` или `cancelled`, просматривать
залы своих ресторанов, создавать залы, просматривать столики своих
ресторанов, создавать столики.

3.4. **Администратор с ролью `admin`** в текущем коде допускается к функциям
менеджера через `requireManager()`, но отдельные административные endpoint'ы
и интерфейс не реализованы.

3.5. Все проверки прав должны выполняться **на сервере**. Клиентские проверки
не считаются защитой.

## 4. Функциональные требования

### 4.1. Регистрация, вход, выход, текущий пользователь

4.1.1. `POST /api/auth/register` — регистрация. Принимает `name`, `email`,
`password`. Пароль не менее 6 символов. Email проверяется через
`FILTER_VALIDATE_EMAIL`. Email должен быть уникальным. Пароль хешируется
через `password_hash(..., PASSWORD_DEFAULT)`. После регистрации создаётся
сессия, выполняется `session_regenerate_id(true)`. Роль нового
пользователя — `user`.

4.1.2. `POST /api/auth/login` — вход. Принимает `email`, `password`.
Проверяет пользователя по email и пароль через `password_verify()`.
При успехе выполняется `session_regenerate_id(true)`, в `$_SESSION['user']`
сохраняются `id`, `name`, `email`, `role`.

4.1.3. `POST /api/auth/logout` — выход. Очищает сессию, удаляет cookie
сессии, вызывает `session_destroy()`.

4.1.4. `GET /api/auth/me` — возвращает текущего пользователя из сессии.
Если сессии нет — ошибка 401.

### 4.2. Рестораны

4.2.1. `GET /api/restaurants` — список ресторанов. Поддерживает параметры
`search`, `cuisine`, `limit`, `offset`.

4.2.2. `GET /api/restaurant/{id}` — карточка ресторана по ID.

4.2.3. Ресторан должен содержать: название, кухню, адрес, город, описание,
рейтинг, изображение, статус. Статусы: `draft`, `published`, `blocked`.

### 4.3. Доступность столиков

4.3.1. `GET /api/tables/availability` — список свободных столиков. Параметры:
`restaurantId`, `date`, `time`, `guests`.

4.3.2. При проверке доступности должны учитываться дата, время, количество
гостей и вместимость столика.

4.3.3. Занятыми считаются брони со статусами `pending` и `confirmed`
на ту же дату и пересекающийся временной интервал. Длительность брони —
**90 минут**.

### 4.4. Бронирование

4.4.1. `POST /api/bookings` — создание брони. Доступно авторизованному
пользователю. Принимает `table_id`, `booking_date` в формате `YYYY-MM-DD`,
`booking_time`, `guests`.

4.4.2. Создание брони выполняется в **транзакции**. Сначала выполняется
`SELECT ... FOR UPDATE` по столику. Затем проверяется пересечение
с существующими бронями. Если пересечение есть — ошибка 409. Если нет —
создаётся запись со статусом `pending`.

4.4.3. `GET /api/bookings/me` — мои брони. Доступно авторизованному
пользователю. Поддерживает фильтр `status`.

4.4.4. `PUT /api/bookings/cancel/{id}` — отмена брони. Пользователь может
отменить только свою бронь. Менеджер может отменить бронь своего ресторана.
Повторная отмена невозможна.

4.4.5. Статусы брони: `pending`, `confirmed`, `cancelled`.

### 4.5. Панель менеджера

4.5.1. `GET /api/manager/bookings` — список броней ресторанов менеджера.
Поддерживает фильтры `status`, `date`. Выборка обязательно ограничивается
`WHERE r.manager_id = ?`.

4.5.2. `PUT /api/manager/booking/{id}` — смена статуса брони. Допустимые
статусы: `confirmed`, `cancelled`. Перед изменением проверяется, что бронь
относится к ресторану менеджера.

4.5.3. `GET /api/manager/halls` — список залов ресторанов менеджера.

4.5.4. `POST /api/manager/halls` — создание зала. Принимает `name`,
`capacity`. `restaurant_id` определяется по менеджеру, а не берётся из формы.

4.5.5. `GET /api/manager/tables` — список столиков ресторанов менеджера.

4.5.6. `POST /api/manager/tables` — создание столика. Принимает `hall_id`,
`number`, `seats`. Перед созданием проверяется, что зал принадлежит ресторану
менеджера.

### 4.6. Личный кабинет

4.6.1. `PUT /api/user/profile` — обновление профиля. Принимает `name`,
`email`, `phone`. Email должен быть уникальным. После обновления данные
сессии синхронизируются.

4.6.2. `PUT /api/user/password` — смена пароля. Принимает `current_password`,
`new_password`. Новый пароль не менее 6 символов. Текущий пароль проверяется
через `password_verify()`.

## 5. База данных

5.1. База данных: `restaurant_booking`, кодировка `utf8mb4`,
collation `utf8mb4_unicode_ci`.

5.2. Таблица `users`: `id`, `name`, `email` уникальный, `phone`,
`password_hash`, `role` (user, manager, admin), `created_at`.

5.3. Таблица `restaurants`: `id`, `manager_id` (FK на `users.id`,
ON DELETE SET NULL), `name`, `cuisine`, `address`, `city`, `description`,
`rating`, `image_url`, `status` (draft, published, blocked), индекс
`idx_city_cuisine` (city, cuisine).

5.4. Таблица `halls`: `id`, `restaurant_id` (FK на `restaurants.id`,
ON DELETE CASCADE), `name`, `capacity`.

5.5. Таблица `tables`: `id`, `hall_id` (FK на `halls.id`, ON DELETE CASCADE),
`number`, `seats`, `x`, `y`, уникальный ключ `uniq_hall_number` (hall_id, number).

5.6. Таблица `bookings`: `id`, `user_id` (FK на `users.id`, ON DELETE CASCADE),
`table_id` (FK на `tables.id`, ON DELETE CASCADE), `booking_date`,
`booking_time`, `guests`, `status` (pending, confirmed, cancelled), `comment`,
`created_at`, индексы `idx_table_date`, `idx_user_date`.

5.7. Таблица `reviews`: `id`, `user_id` (FK на `users.id`, ON DELETE CASCADE),
`restaurant_id` (FK на `restaurants.id`, ON DELETE CASCADE), `rating`, `text`,
`created_at`. API для отзывов в текущем MVP не реализован.

5.8. Демо-данные: пользователи `manager@demo.ru` и `user@demo.ru`,
рестораны «Пушкинъ» и «White Rabbit», залы «Основной зал» и «Веранда»,
столики №1, №2, №5, №8.

## 6. REST API

6.1. Общие правила: все ответы JSON; успех — `{ "data": ... }`;
ошибка — `{ "error": "..." }`; методы: GET, POST, PUT, PATCH, DELETE, OPTIONS;
для авторизованных запросов используются cookie сессии; CORS разрешает
credentials.

6.2. Для всех защищённых endpoint'ов сервер обязан вызывать `authenticate()`
и, где нужно, `requireManager()` или `requireRole()`.

6.3. Для менеджерских endpoint'ов обязательна привязка к ресторану менеджера.
Нельзя доверять `restaurant_id`, `hall_id`, `table_id`, пришедшим с клиента,
без проверки владельца.

## 7. Обработка ошибок

7.1. Исключения серверной части: `AuthException` → 401; `ForbiddenException`
→ 403; `NotFoundException` → 404; `ConflictException` → 409; прочие
`Throwable` → 500.

7.2. Если endpoint не найден, возвращается 404 и
`{ "error": "Endpoint not found" }`.

7.3. Ошибка подключения к БД возвращает 500 и
`{ "error": "DB connection failed" }`.

7.4. Внутренние ошибки логируются через `error_log()`, клиенту отдаётся
общее сообщение `Internal server error`.

7.5. Запрещено перезаписывать корректный HTTP-код (401/403/404/409) на 500
в общем catch-блоке.

## 8. Безопасность

8.1. Сессии: `session_start()` выполняется только через `bootstrapSession()`.
Параметры cookie: `httponly = true`, `samesite = Strict`,
`secure = true` при HTTPS.

8.2. После login и register обязательно вызывается
`session_regenerate_id(true)` для защиты от session fixation.

8.3. Пароли хранятся только в виде хеша `password_hash()`. Проверка —
`password_verify()`.

8.4. Все SQL-запросы выполняются через подготовленные выражения PDO.
Конкатенация пользовательских данных в SQL недопустима.

8.5. Защита от IDOR: менеджер видит и изменяет только те брони, залы
и столики, которые относятся к ресторанам
с `manager_id = $_SESSION['user']['id']`.

8.6. CORS: при наличии `HTTP_ORIGIN` возвращаются заголовки
`Access-Control-Allow-Origin`, `Access-Control-Allow-Credentials: true`,
разрешённые методы и заголовки. В production origin должен быть ограничен
конкретным доменом.

8.7. CSRF: в текущем коде заголовок `X-CSRF-Token` разрешён в CORS,
но проверка токена не реализована. Для production рекомендуется добавить
CSRF-токен для изменяющих запросов.

8.8. Транзакции: создание брони выполняется в транзакции с блокировкой
столика `FOR UPDATE`, чтобы исключить race condition и двойное бронирование.

## 9. Клиентский интерфейс

9.1. Страницы: `index.html` — главная; `restaurants.html` — каталог;
`restaurants-react.html` — альтернативный каталог на React (демонстрация);
`restaurant-detail.html` — карточка и бронирование; `login.html` — вход;
`register.html` — регистрация; `profile.html` — личный кабинет;
`manager.html` — панель менеджера.

9.2. JS-модули: `api.js` — обёртка над fetch; `auth.js` — проверка
авторизации и отображение ссылок; `profile.js` — личный кабинет;
`booking.js` — доступность и создание брони; `manager.js` — панель
менеджера. Файл `booking.js` должен быть подключён только там, где он реально
существует, иначе возникает 404.

9.3. `api.js` должен использовать `credentials: 'include'`, отправлять JSON,
корректно разбирать ответ и выбрасывать ошибку при `!response.ok`.

9.4. `auth.js` должен определять глобальную функцию `checkAuth()`, вызывать
`GET /api/auth/me`, при успехе вызывать `showUser(user)`.

9.5. `showUser()` должен переключать видимость через CSS-класс `hidden`,
а не через inline-style. Для роли `manager` должна добавляться ссылка
на `manager.html`.

9.6. В CSS должны быть определены классы: `restaurant-grid`, `profile-tabs`,
`tab-btn`, `tab-panel`, `booking-card`, `empty-state`, `user-info`, `hidden`.
Дополнительно используются CSS-переменные `--rb-primary`, `--rb-primary-dark`,
`--rb-bg`, `--rb-text`, `--rb-muted`, `--rb-radius`, `--rb-shadow`
для согласованности цветов и адаптации под Bootstrap 5.

9.7. Основные элементы интерфейса: поисковая строка, фильтр по кухне,
карточки ресторанов, форма выбора даты/времени/гостей, сетка свободных
столиков, кнопка бронирования, список броней, фильтр статусов, вкладки
профиля, панель менеджера со статистикой, таблицей броней, управлением
залами и столиками.

## 10. Нефункциональные требования

10.1. Система должна работать в современных браузерах: Chrome, Firefox,
Safari, Edge.

10.2. Время отклика API на типовых операциях — до 1–2 секунд при локальном
развёртывании.

10.3. Код должен быть совместим с PHP 8+ и MySQL 5.7+/8.0.

10.4. Все изменяющие операции должны быть защищены от несанкционированного
доступа.

10.5. Схема БД должна поддерживать целостность через внешние ключи
и каскадные удаления.

10.6. Логирование ошибок обязательно. Пользователь не должен видеть
stack trace.
