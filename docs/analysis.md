# Анализ предметной области

## 1. Проблема

Существующие системы онлайн-бронирования столиков (OpenTable, Restoplace, Tomato)
либо перегружены функциями, либо требуют платной подписки, либо используют
тяжёлый стек (Node.js + React + PostgreSQL + JWT), что усложняет развёртывание
на типовом хостинге. Малым и средним ресторанам нужна простая, лёгкая система
бронирования на PHP + MySQL без сторонних фреймворков.

## 2. Целевая аудитория

| Роль | Кто это | Потребности |
|------|---------|-------------|
| Гость | Неавторизованный пользователь | Просмотр ресторанов, поиск, проверка доступности |
| Клиент (user) | Авторизованный пользователь | Бронирование, просмотр своих броней, профиль |
| Менеджер (manager) | Сотрудник ресторана | Управление бронями/залами/столиками своих ресторанов |
| Администратор (admin) | Владелец системы | Полный доступ через requireManager() |

## 3. Бизнес-процессы

1. Регистрация/вход клиента.
2. Поиск ресторана по названию, городу, кухне.
3. Проверка доступности столиков на дату/время/число гостей.
4. Создание брони со статусом pending.
5. Обработка брони менеджером → confirmed или cancelled.
6. Отмена брони клиентом.
7. Управление залами и столиками менеджером.

## 4. Ограничения

- Один менеджер привязан к одному или нескольким ресторанам.
- Столик принадлежит ровно одному залу.
- Бронь привязана к конкретному столику и пользователю.
- Длительность брони — 90 минут (по ТЗ).
- Занятые брони — статусы pending и confirmed.
- Пароли хранятся в виде хеша password_hash.
- Аутентификация — PHP-сессии (без JWT).

## 5. Аналоги

| Аналог | Плюсы | Минусы |
|--------|-------|--------|
| OpenTable | Мировой лидер, огромная база | Сложный, платный, не адаптирован под РФ |
| Restoplace | Российский, интеграция с CRM | Платный, требует обучения |
| Tomato | Простой интерфейс | Ограниченный функционал |
| RestBook (наш) | Простой, лёгкий, REST API, ролевая модель | Только базовый функционал |
